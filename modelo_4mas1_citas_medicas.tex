\section{Introducción al modelo 4+1}

Antes se respondió a la pregunta:

\begin{quote}
\textbf{¿Cómo podemos organizar nuestro sistema?}
\end{quote}

Para el sistema de gestión de citas médicas se identificaron componentes, responsabilidades, relaciones, capas, base de datos y usuarios. Sin embargo, esta arquitectura no muestra absolutamente todo lo que necesitamos conocer. Diferentes participantes hacen preguntas distintas:

\begin{itemize}
    \item El gerente podría preguntar: \textbf{¿Qué funcionalidades importantes tiene el sistema?}
    \item El desarrollador podría preguntar: \textbf{¿Cómo está organizado el software?}
    \item El administrador de infraestructura podría preguntar: \textbf{¿En qué servidores se ejecutará?}
    \item El responsable técnico podría preguntar: \textbf{¿Qué procesos se ejecutan simultáneamente?}
\end{itemize}

Por eso se utilizan diferentes perspectivas de una misma arquitectura. El Modelo 4+1, propuesto por Philippe Kruchten, describe la arquitectura mediante cinco perspectivas: vista lógica, vista de procesos, vista de desarrollo, vista física y vista de escenarios (+1).

\begin{tabularx}{\textwidth}{>{\bfseries}p{0.23\textwidth}X}
\toprule
Vista & Pregunta principal\\
\midrule
Lógica & ¿Qué partes funcionales tiene el sistema?\\
Procesos & ¿Cómo se ejecutan e interactúan los procesos?\\
Desarrollo & ¿Cómo está organizado el software para desarrollarlo?\\
Física & ¿Dónde se ejecuta el sistema?\\
Escenarios & ¿Qué situaciones importantes debe poder realizar el sistema?\\
\bottomrule
\end{tabularx}

\section{PRACTICA 1: Vista lógica}

\textbf{Cada uno debe tomar la arquitectura de la Clase 1 y responder:}

\subsection*{Paso 1}
\textbf{Identifique los principales componentes funcionales.}

Para el sistema de gestión de citas médicas se identifican:
\begin{itemize}
    \item Pacientes: entidad externa con datos personales, contacto, consentimiento y estado.
    \item Médicos: entidad interna con especialidad, horarios, disponibilidad y estado profesional.
    \item Agenda y citas: programación, consulta, modificación, cancelación y estados de citas.
    \item Atención clínica: registro de diagnóstico, consulta, prescripción e insumos utilizados.
    \item Cobros y caja: registro del pago y control del cierre diario.
    \item Usuarios, roles y auditoría: autenticación, permisos y trazabilidad.
    \item Reportes: consultas de agenda, atención, cobros y productividad.
    \item Base de datos: persistencia de pacientes, médicos, citas, atenciones y cobros.
\end{itemize}

\subsection*{Paso 2}
\textbf{Escriba la responsabilidad de cada componente.}

\begin{tabularx}{\textwidth}{>{\bfseries}p{0.30\textwidth}X}
\toprule
Componente & Responsabilidad\\
\midrule
Pacientes & Conservar los datos administrativos del paciente externo y su relación con las citas.\\
Médicos & Mantener especialidad, horarios y disponibilidad del profesional interno.\\
Agenda y citas & Validar disponibilidad, evitar solapamientos y controlar el estado de cada cita.\\
Atención clínica & Registrar diagnóstico, consulta, prescripción e insumos consumidos.\\
Cobros y caja & Asociar pagos con citas y controlar el arqueo diario.\\
Usuarios y auditoría & Aplicar permisos y registrar operaciones sensibles.\\
Reportes & Consultar información consolidada sin modificar transacciones.\\
Base de datos & Guardar información y mantener relaciones e integridad.\\
\bottomrule
\end{tabularx}

\subsection*{Paso 3}
\textbf{Determine qué componentes se relacionan.}

\begin{enumerate}
    \item Pacientes proporciona sus datos a Agenda y citas.
    \item Médicos proporciona horarios y disponibilidad a Agenda y citas.
    \item Agenda y citas entrega la cita a Atención clínica y Cobros y caja.
    \item Atención clínica registra diagnósticos y solicita actualizar consumos.
    \item Cobros y caja registra el pago asociado a la cita.
    \item Usuarios y auditoría autoriza las operaciones de cada rol.
    \item Todos los componentes persistentes utilizan la Base de datos mediante servicios.
\end{enumerate}

\subsection*{Paso 4}
\textbf{Construya la Vista Lógica.}

La vista lógica se construye con los componentes y relaciones anteriores. Paciente y Médico se representan por separado porque cumplen funciones diferentes: el paciente es una entidad externa que solicita o recibe el servicio; el médico es un usuario interno que presta el servicio profesional.

\subsection*{Paso 5}
\textbf{¿Cómo está organizado funcionalmente nuestro Sistema de Control de Inventarios?}

Para este proyecto, la respuesta adaptada es: el sistema está organizado funcionalmente como un sistema de gestión de citas médicas. Pacientes solicita o recibe el servicio; Médicos ofrece disponibilidad y registra la atención; Agenda y citas coordina la programación; Atención clínica conserva el diagnóstico; Cobros y caja registra el pago; Usuarios y auditoría protege el acceso; Reportes consulta la información y Base de datos conserva las relaciones.

\section{PRACTICA 2: Vista de procesos}

La vista lógica nos decía: \textbf{¿Qué partes tiene el sistema?} La vista de procesos pregunta: \textbf{¿Cómo se ejecutan los procesos y cómo interactúan durante la ejecución?}

\textbf{Cada uno seleccione un proceso importante.}

\textbf{Recomendación: Registrar Venta}

Para el sistema de la clínica se selecciona como proceso equivalente \textbf{Programar y atender una cita médica}, porque integra REQ01, REQ02, REQ03, REQ04 y REQ05.

\textbf{Luego deberá representar:}
\begin{enumerate}
    \item \textbf{quién inicia el proceso:} el paciente solicita la cita y Recepción inicia el registro.
    \item \textbf{qué proceso se ejecuta:} Agenda y citas consulta la disponibilidad del médico.
    \item \textbf{qué componentes participan:} Pacientes, Médicos, Agenda y citas, Atención clínica, Cobros y caja, Usuarios y auditoría y Base de datos.
    \item \textbf{qué información intercambian:} datos del paciente, fecha, hora, médico disponible, identificador de cita, diagnóstico, prescripción, consumo y pago.
    \item \textbf{qué proceso se ejecuta después:} si el horario está disponible, se guarda la cita; después el médico registra el diagnóstico y caja registra el pago.
    \item \textbf{cómo termina:} la cita cambia a Atendida y la información queda disponible para futuras consultas autorizadas.
\end{enumerate}

La validación de disponibilidad evita que un médico tenga dos citas activas en el mismo intervalo. Si no existe disponibilidad, el sistema informa el conflicto y permite seleccionar otro horario.

\section{PRACTICA 3: Vista de desarrollo}

\textbf{¿Cómo organizaremos el software para poder desarrollarlo y mantenerlo?}

La vista de desarrollo, también conocida como vista de implementación, representa cómo está organizado el software desde la perspectiva del desarrollo y mantenimiento.

\textbf{Cada uno deberá construir una estructura similar a:}

\begin{quote}
Sistema de Inventarios\par
Presentación\par
Lógica de negocio\par
Acceso a datos
\end{quote}

Para el sistema de citas médicas la estructura equivalente es:

\begin{enumerate}
    \item \textbf{Presentación}
    \begin{itemize}
        \item Pacientes.
        \item Médicos.
        \item Agenda y citas.
        \item Atención clínica.
        \item Cobros.
        \item Reportes.
    \end{itemize}
    \item \textbf{Lógica de negocio}
    \begin{itemize}
        \item Gestión de pacientes.
        \item Gestión de médicos y disponibilidad.
        \item Gestión de citas.
        \item Gestión de atención y diagnósticos.
        \item Gestión de cobros.
        \item Seguridad y auditoría.
    \end{itemize}
    \item \textbf{Acceso a datos}
    \begin{itemize}
        \item Repositorio de pacientes y médicos.
        \item Repositorio de citas y agenda.
        \item Repositorio de atenciones y diagnósticos.
        \item Repositorio de cobros y auditoría.
    \end{itemize}
\end{enumerate}

La presentación no consulta directamente la base de datos. La lógica de negocio aplica las reglas, como no solapar citas y controlar permisos. El acceso a datos persiste la información. Esta organización permite que los cambios estén controlados, las responsabilidades estén separadas y el código sea mantenible.

\section{PRACTICA 4: Vista física}

\textbf{¿Dónde se ejecutará nuestro Sistema de Control de Inventarios?}

Para este proyecto, la respuesta adaptada es que el Sistema de Gestión de Citas Médicas se ejecutará en una infraestructura centralizada:

\begin{enumerate}
    \item Usuarios: recepción, médicos, administración y gerencia.
    \item Computadoras o dispositivos móviles autorizados.
    \item Red segura mediante HTTPS y control de acceso.
    \item Servidor de aplicación que ejecuta la interfaz y los servicios de negocio.
    \item Servidor de base de datos que conserva pacientes, médicos, citas, diagnósticos, pagos y auditoría.
    \item Servicio de respaldo y notificaciones para copias de seguridad y confirmaciones.
\end{enumerate}

La propuesta se justifica porque centraliza la información de la clínica, facilita el mantenimiento, permite aplicar permisos y simplifica los respaldos. La base de datos puede permanecer en una red privada separada del servidor de aplicación.

\section{PRACTICA 5: Vista de escenarios (+1)}

La pregunta es: \textbf{¿Qué situaciones importantes debe poder realizar el sistema?}

Un escenario representa una situación concreta en la que el sistema es utilizado. Para la clínica se seleccionan los siguientes escenarios:

\begin{enumerate}
    \item Programar una cita.
    \item Modificar o cancelar una cita.
    \item Registrar un diagnóstico.
    \item Consultar la agenda médica.
    \item Registrar un cobro.
\end{enumerate}

\textbf{Ahora integre las cinco perspectivas.}

\subsection*{Paso 1 — Vista lógica}
\textbf{Identificar:}
\begin{itemize}
    \item componentes: Pacientes, Médicos, Agenda, Atención, Cobros, Seguridad, Reportes y Base de datos;
    \item módulos: presentación, negocio y acceso a datos;
    \item relaciones: datos del paciente, disponibilidad médica, citas, diagnósticos y pagos.
\end{itemize}

\subsection*{Paso 2 — Vista de procesos}
\textbf{Seleccionar un proceso importante.}

\textbf{Recomendado: Registrar Venta}

Para el sistema médico se utiliza Programar y atender una cita, representando inicio, procesos, interacción, información y finalización. El paciente inicia; Recepción registra; Agenda valida; Médicos proporciona disponibilidad; Atención registra diagnóstico; Cobros registra el pago y la Base de datos conserva el resultado.

\subsection*{Paso 3 — Vista de desarrollo}
\textbf{Representar:}

\begin{quote}
Presentación\par
↓\par
Negocio\par
↓\par
Datos
\end{quote}

Se colocan los módulos de pacientes, médicos, agenda, atención, cobros, seguridad, reportes y repositorios.

\subsection*{Paso 4 — Vista física}
\textbf{Representar:}

\begin{quote}
Usuarios\par
↓\par
Equipos\par
↓\par
Servidor\par
↓\par
Base de datos
\end{quote}

\subsection*{Paso 5 — Escenarios}
\textbf{Seleccionar mínimo 3 escenarios importantes.}

Se seleccionan cinco: Programar cita, Modificar o cancelar cita, Registrar diagnóstico, Consultar agenda y Registrar cobro.

\textbf{Responder estas preguntas:}

\begin{enumerate}
    \item \textbf{Lógica: ¿Nuestra arquitectura tiene todos los componentes necesarios?} Sí. Incluye Pacientes, Médicos, Agenda, Atención, Cobros, Seguridad, Reportes y Base de datos.
    \item \textbf{Procesos: ¿Los componentes pueden interactuar para ejecutar nuestros procesos?} Sí. Las relaciones de la vista lógica se convierten en mensajes y pasos del proceso de citas.
    \item \textbf{Desarrollo: ¿Podemos organizar el software de manera que sea mantenible?} Sí. La vista de desarrollo separa presentación, negocio y datos por módulos.
    \item \textbf{Física: ¿La infraestructura propuesta permite ejecutar el sistema?} Sí. Los usuarios se conectan desde sus equipos al servidor de aplicación y este utiliza una base de datos central.
    \item \textbf{Escenarios: ¿Nuestra arquitectura puede soportar los casos de uso importantes?} Sí. Programar, cancelar, atender, consultar y cobrar utilizan los componentes definidos en las demás vistas.
\end{enumerate}

Si alguna respuesta es NO, identificar qué parte de la arquitectura necesitan revisar. En esta propuesta no se identifica una respuesta negativa, porque las cinco vistas mantienen los mismos componentes y cuentan una historia coherente del sistema de citas médicas.

\section{PRACTICA 6}

\textbf{Cada uno haga su propia investigación de la herramienta CASE que puede utilizar para crear un archivo que le permita crear la arquitectura de nuestra práctica inventario y luego pueda compartir el enlace para ser evaluado.}

La herramienta seleccionada es diagrams.net (draw.io). Es adecuada porque permite organizar el trabajo en páginas, editar diagramas, importar y exportar XML y compartir el archivo mediante GitHub.

El archivo CASE contiene:
\begin{itemize}
    \item Página 1 → Arquitectura General.
    \item Página 2 → Vista Lógica.
    \item Página 3 → Vista de Procesos.
    \item Página 4 → Vista de Desarrollo.
    \item Página 5 → Vista Física.
    \item Página 6 → Escenarios.
\end{itemize}

El criterio más importante es la coherencia. No tendría sentido que en la vista lógica aparezca un módulo de Agenda, pero en la vista de procesos nunca participe Agenda y en los escenarios tampoco aparezca. En este trabajo Agenda aparece en la vista lógica, participa en el proceso de programar citas, se organiza en Presentación y Negocio, se ejecuta en el servidor de aplicación y participa en los escenarios de programación, modificación y consulta.
